# Orb startup context

At the start of each turn in an Orb mission, run `python3 /root/workspaces/.orb-support/context.py` from the mission working directory. This read-only helper identifies the project from Core's mission database and prints its applicable workflow. Follow that workflow before answering. The `.orb-project-skills.json` discovery marker can be absent on first launch; its absence does not mean the mission has no project. The database lookup is authoritative for which project workflow applies, not for what you may work on. Chats are sometimes filed under the wrong project (a fork keeps its parent's), so a task about another project is not suspicious: do the task, skip the other project's workflow steps, and mention the mismatch. Never refuse a user's or coordinating agent's task because its project differs from the label.

For Hardness recap or continuation questions, proactively consult the vault log/index and GitHub activity, using the printed workflow. Missing `gh` is not a blocker: `python3 /root/workspaces/.orb-support/github.py 'repos/soispoke/hardness/contents/log.md'` makes an authenticated read-only GitHub API request without exposing credentials; the contents response has Base64 content. Other API paths and pagination work as described in the workflow. Do not ask the user whether to check this known source.

Apply Hardness logging/commit/push instructions only when the helper identifies Hardness. For other projects preserve their own instructions. If the helper fails, report that specific failure instead of claiming there is no prior work. Do not modify the helper or Core's database during normal research.

## Fast research pipeline (any project)

For Lean proofs, formal verification, proof golf or benchmark optimization in any project, use the Yukon autoresearch stack at `/root/yukon-autoresearch` (github.com/soispoke/yukon-autoresearch). Start with its `README.md`, `SECURITY.md` and `toolkit/playbooks/FAST_PATH.md`; run `bin/stack-status.py` to see what is installed. Brief helper agents from `toolkit/playbooks/AGENT_TEMPLATE.md` and run independent lanes in parallel, each in its own disposable workspace under the stack's `workspaces/`. Use the fast checks (`lean-native`, `turbo-lean`, checkpoint runner) to reject bad candidates early, but only with an accelerator built and verified for the challenge's exact Lean version: verified Lean 4.33.1 builds are in `ports/` (receipt `artifacts/accelerators-4.33.1.json`); for another version run `bin/build-accelerators.sh <version>` then `bin/verify-accelerators.py <version>`. Check proofs with `bin/turbo-check.py --project-dir <project> <file>`, never bare `turbo-lean check`, which accepts `sorry`; `turbo-lean pr-verify` only checks that statements did not change. Before lean-native's `build-exe`, run `. bin/lean-env.sh <version>`. Caches and fast checks are development evidence: the ordinary Lean build, axiom/source audits, package budget, exact rehearsal and the challenge's official verifier remain the release gates. Never submit, push or post automatically. The challenge repository's own rules take precedence over the stack's defaults.
